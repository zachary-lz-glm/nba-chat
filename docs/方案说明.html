NBA Chat 方案说明

NBA 场边智能问答 Demo · 笔试题交付 在线体验：NBA Chat(即开即用,无需配置;大陆网络访问 vercel.app 需自备代理) 文档更新日期：2026-10-12（北京时间）。对应最近已验证的上线代码 48ce366。本文区分当前实现、交付验证与旧版评测记录；历史模型评测与成本样本见 scripts/eval-results.md，不代表新版已通过全部 31 题复测。

1. 总体思路

以「每一场比赛，都值得看懂」为产品主张，做一个从赛程进入、围绕具体比赛持续追问的中文 Agent Demo。使用 NBA 视觉元素进行概念设计，不代表 NBA 官方发布的产品。

目标手段验证
事实可追溯结构化卡片来自工具结果；纯单场球员统计正文由校验后的查询数据生成；开放式分析保留模型输出当前真实模型统计联调通过，旧版 31 题评测单独保留；不承诺所有回答完全准确
体验连贯今日赛程入口、流式输出、比分上下文、统计卡片与逐回合追问；本机历史会话当前桌面与手机交互验证通过；本次线上单场统计样本约 5 秒，非性能分位数
合规稳健六类红线话题按提示与查询策略引导回赛场旧版 I1-I7 及记录中的变体通过；新版未重跑完整红线评测
即开即用站方默认阿里云百炼服务，保留站方自选模型与 BYOK 设置当前默认档生产联调通过；三档 7 例冒烟属于旧版验证

一个贯穿全程的判断:评分权重里事实准确性 20% + 安全合规一票否决,而幻觉恰恰是 LLM 问答的默认失败模式。所以方案的重心不在花哨功能,而在「用工具纪律 + 评测回路把事实错误压到最低」,并把每一步的实测结果(包括失败的)如实写进本文。

1.1 当前产品体验

  • 首页采用深海军蓝、NBA 红与球场背景，主标题为「每一场比赛，都值得看懂」。背景与篮球缩略图为依据设计稿重建的 AI 氛围图，不代表某场真实赛事；球队标识来自 NBA 官方球队页公开 CDN。
  • 默认展示北京时间「今天」，支持「昨天」和固定日期 2025-06-23 的「经典比赛」。推荐卡优先选择进行中的比赛，其次是未开赛的比赛，最后选择当天较晚的完赛记录。其余全部比赛放在「更多对阵」横向列表；当天只有一场时不显示该区域。
  • 未开赛显示赛前看点与球队近况；进行中显示实时战况与球员数据；完赛显示复盘与最后两分钟；延期或取消显示赛程状态，不以 0:0 冒充当前比分。
  • 聊天保留顶部比赛上下文，支持上半场、第三节、末节和最后两分钟记录查询。时间线可展开、收起，并基于具体日期、球队和回合继续追问；这些入口不是预填的分析结论。
  • 手机端更多菜单包含新建会话、历史对话和设置。支持停止生成、复制回答、会话切换、日期标签键盘操作和弹层关闭后的焦点恢复。

2. 架构

浏览器（Next.js / React）
  ├─ 今日 / 昨日 / 经典比赛 → GET /api/games
  ├─ useChat / 比分上下文 / 统计卡 / 回合时间线
  ├─ 历史会话与模型设置 → localStorage
  └─ 当前会话消息 → POST /api/chat
                              │
Vercel Serverless             ▼
  ├─ 北京时间与赛季上下文 / 模型解析 / 查询策略
  ├─ 百炼模型 + AI SDK 多步工具循环（最多 16 步）
  ├─ 10 个工具 → ESPN / 中文维基 → 数据压缩
  ├─ 单场统计与复盘的证据补查
  ├─ 纯单场球员统计 → 校验数据后生成表格
  └─ 其他回答 → 模型流式正文 / 实例内存限流
  • 未接会话数据库：比赛数据来自外部公开服务；历史会话存在本机浏览器。对话生成仍会向服务器与模型服务发送当前会话上下文，不能将本地持久化理解为数据始终不离开设备。
  • 服务端取数:ESPN 调用全部在 Vercel 服务端完成,避免浏览器直连的 CORS 限制；外部数据源仍可能超时、限流或不可用。
  • 单问生命周期:用户输入 → 注入动态系统提示 → qwen-plus 决策 → 工具调用(ESPN → 压缩)→ 多步循环(≤16)→ 纯单场统计校验结果并生成表格，其他问题保留模型正文 → 流式响应回浏览器 → 渲染卡片/状态条 → 显示耗时。
  • 技术栈:Next.js 16(App Router)+ React 19 + TypeScript + Tailwind CSS 4;Vercel AI SDK(ai v7 + @ai-sdk/openai-compatible)接阿里云百炼 compatible-mode;react-markdown + remark-gfm 流式渲染;use-stick-to-bottom 吸底;vitest 单测 77 项。

2.1 会话与设置保存

项目当前规则
历史位置本机浏览器 localStorage，键为 nba-chat-sessions；不做云端会话同步
内容与容量保存标题、消息、工具结果和更新时间；最多 50 个会话，超过后淘汰最久未更新的会话

隔离与边界不同设备、浏览器及域名独立；无痕会话结束后通常清除。未实现存储配额不足时的恢复提示，不能保证永久保存

3. 数据方案与实测记录

数据源只有两个:ESPN 公开 JSON 端点(赛程/赛果/单场/逐回合/排名/球员/新闻,无需鉴权)+ 中文维基百科(历史背景、历年冠军列表)。不依赖任何内部库或付费数据。

工具层 10 个:get_games_by_date、get_game_box、get_game_plays、get_series_or_games_lookup(≤35 天区间)、get_standings、search_player、get_player_stats、get_player_gamelog、get_champions、get_news_or_wiki。

以下结论来自项目已记录的端点实测。ESPN 公开 JSON 接口不是本项目拥有的稳定服务契约，字段与可用性变化仍需监测：

端点/字段实测结论(踩坑记录)
scoreboard dates 参数按美东日历日组织。北京某日需查美东 D-1、D 两天,再按事件 UTC 时间戳回滤北京窗口(北京时间上午的比赛属于美东前一天)
scoreboard series系列赛大比分自带(series.summary 如 "OKC Leads 3-2"),不必逐场累加
scoreboard seasontype 1/2/3 = 季前/常规/季后赛,据此生成「2026-27 季前赛」标签，修复已复现的赛事阶段误标
summary(box)两队球员名单对齐;压缩为每队按出场时间前 9 人、列裁剪 MIN/PTS/REB/AST/FG/3PT/FT/±
summary(plays)支持最后 N 秒(仅第四节及加时)/仅得分回合/按节过滤;压缩后逐回合表与 ESPN 官网逐条一致
search uid球员数字 id 藏在 uid 字符串里(s:40~l:46~a:4278073 → 4278073),需解析而非现成字段
gamelogseasonTypes 分组结构(Regular Season / Postseason,后者含总决赛场次);season 参数是结束年(2024-25 赛季→2025)——早期文档误标为起始年,曾直接导致赛季标注错误(A3/A2/D1)
stats该端点忽略 season 参数,恒为生涯聚合(seasontype 2/3 区分常规/季后)。评测中模型曾把生涯场均 25.3 误当赛季值(真实赛季值 31.9),修复方式:工具返回值显式标注「career 为生涯聚合」,并强制单季场均以 gamelog 分组汇总为准
中文维基冠军列表简体页是重定向,须抓繁体页 wikitext;繁体队名(奧克拉荷馬雷霆/俄克拉何马城雷霆、印第安那溜馬等)需归一映射;解析出近 30 年年份→冠军/总决赛比分/亚军,压缩至 ~3.2KB

压缩层是成本与质量的关键:ESPN 原始响应单场可达 500KB+(逐回合全量),直接进上下文既慢又贵。压缩后工具结果 1-8KB,且在 gamelog 侧预先按组算好场均,避免模型心算出错。

4. 时间与赛季

问题方案
「今天/昨天」按谁的日历算三级换算:北京日历日 → 美东日期区间(北京一日恒覆盖美东 D-1 与 D 两天,夏冬令时均成立)→ 按事件 UTC 时间戳回滤北京窗口。评测 J2「昨天比赛」7 场比分/开球时间全对
赛季怎么算动态注入:10 月起属新赛季(注意 10 月上中旬可能是季前赛,以工具返回标签为准)、4-6 月季后赛、7-9 月休赛期「本赛季」指刚结束赛季
season 传参口径统一为赛季结束年(2024-25→2025),写死在提示词与全部工具描述里(实测曾错标,已修)
无年份指代「G7/总决赛/上赛季」默认锚定最近发生该事件的赛季,先查证命中再作答,开头注明所指场次
未完场比赛必须标注「比赛进行中」+ 当前节次比分,禁止终场口吻;追问时先说明数据实时变化再给最新比分(评测 K4 通过)

4.1 首页的数据更新机制

首页不是构建时写死的赛程。每次进入首页或切换日期，浏览器会按所选北京时间日期请求 /api/games?date=YYYY-MM-DD；服务端查询 ESPN，按实际开球 UTC 时间过滤当天窗口。

场景当前行为
明天重新打开默认日期重新按北京时间计算，查询明天当天赛程，无需重新部署
页面停留跨零点日期订阅每 60 秒检查一次；页面重新可见也检查，所选「今天 / 昨天」随新日期更新
有进行中比赛页面可见时每 30 秒重新请求所选日期的赛程；「更新」时间表示服务端本次取数时间，不是源数据的发布时刻
全部未开赛或已结束不持续轮询。未开赛页面一直停留到开赛，需手动更新、切换日期或重新打开，才能发现新的直播状态
缓存与实时性接口 max-age=30, stale-while-revalidate=30；访问上游使用 no-store。受短时缓存及 ESPN 更新速度影响，不承诺秒级同步或数据源 SLA
失败与空数据失败提示重新查询，真实空数据提示该日期暂无比赛；不以占位比分或伪造比赛补齐页面

北京时间 2026-10-10 20:03 左右的线上核对：10 月 9 日接口返回 7 场，10 月 10 日返回 1 场（灰熊 104:100 公牛），10 月 11 日返回 8 场预定赛事；同时核对覆盖日期的 ESPN 原始赛程。该数量是一次查询快照，不作为以后日期的固定数据。

5. 可靠性与合规

5.1 查询纪律与统计校验

以下是系统提示中的约束目标，不等同于模型每次都能遵守：

  • 客观数字必须来自工具结果;记忆与工具冲突一律以工具为准(模型的篮球先验可能过时甚至属于另一个数据世界);
  • 用户前提先查证:比分/日期/「某队夺冠过」先核实再作答或纠正;否定性结论(「没打过」)必须先查工具;
  • 主观题数字纪律:分析/战术题中任何具体数字必须来自本轮工具结果,查不到只能定性表述;
  • 禁止声称「已核实」而实际未调用工具;历史案例枚举宁少勿滥,严禁编「全部 N 次」清单。

本次复查发现模型只查询赛果后，仍可能输出未经查询的球员数字和伤病结论。因此补充了两层实现：

  1. 针对已确定具体比赛的统计问题，要求继续调用 get_game_box；复盘或关键转折问题还要求查询 get_game_plays。失败的查询不会无限重试，交由后续响应说明数据不足。
  2. 对识别出的纯单场球员统计意图，直接用 Zod 校验后的工具结果生成得分 / 篮板 / 助攻表格，保留工具进度，替换模型自由发挥的正文。技术统计工具每队保留最多 9 名球员；这不是全名单展示。

赛季统计、比较与开放式分析仍走模型正文，未实现通用的逐句事实核验。基于规则的意图识别也不覆盖所有自然语言表达；已有的单场校验不能被表述为「全面消除幻觉」。

5.2 合规红线(六类,先拒答不检索)

政治地缘/社会争议;场外隐私与绯闻;法律指控与司法细节;黑哨假球等无证据阴谋指控;博彩盘口与涉金钱预测;侮辱性绰号与人身攻击(用侮辱性绰号指代球员时不映射、不给数据)。正常篮球评价与不涉金钱的夺冠预测照常作答。旧版记录中的 I1-I7 及「盘口包装」「造星阴谋包装」「绰号变体」等样本通过；当前版本未重新执行全量红线评测，不据此作零漏过保证。

6.3 成本控制手段与已知限制

  • 压缩层是第一杠杆:500KB→1-8KB 直接把单轮工具结果压掉两个数量级,未压缩方案单问成本将放大 10 倍以上;
  • 限流 12 req/min/IP(内存令牌桶):设计意图是防站方 key 被刷爆。实测诚实披露:Vercel 多实例分布下该内存级实现基本不生效(线上 ~100 次请求未触发一次 429),仅对单实例内的突发有效;彻底方案需引入外部存储(如 Upstash Redis),出于成本与复杂度考量未引入——demo 阶段以 key 用量告警为实际防线;
  • 旧版成本比较中 qwen-flash 更便宜；当前单价需按百炼控制台确认。BYOK 的模型用量由用户所选服务承担，站方仍承担应用托管成本;
  • 不做内置 web_search 兜底的原因之一也是成本:搜索结果体积不可控,且与百炼 compatible-mode 混用受限。
