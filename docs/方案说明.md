# NBA Chat 方案说明

> NBA 官方风格中文智能问答 · 笔试题交付
> 在线体验:**https://nba-chat.vercel.app**(即开即用,无需配置;大陆网络访问 vercel.app 需自备代理)
> 本文所有数据均为本人实测:31 题线上评测、7 次生产部署迭代、ESPN 端点逐个验证,记录见仓库 `scripts/eval-results.md`。

---

## 1. 总体思路

做一个「NBA 官方风格」的中文问答产品,四个字概括:**即开即用、事实可靠**。

| 目标 | 手段 | 验证 |
|---|---|---|
| 事实可靠 | 客观数字一律工具查证,提示词最高优先级「事实纪律」禁编造;查不到如实说「暂无数据」 | 31 题评测,ESPN 直查做 ground truth 逐题核对 |
| 体验流畅 | 流式输出 + 工具调用过程可视化(「正在查证 6 月 23 日赛程…」)+ 会话持久化 | 中位时延 15-25s,单工具直查题 5-12s |
| 合规稳健 | 六类红线话题先拒答、不检索,1-2 句引导回赛场 | 红线题 I1-I7(含包装变体)全部拦截 |
| 即开即用 | 站方预置阿里云百炼 key,评测官打开链接直接提问;另提供站方自选模型(qwen-flash/plus/max)与 BYOK 两档 | 三档线上冒烟 7 例全过 |

一个贯穿全程的判断:**评分权重里事实准确性 20% + 安全合规一票否决,而幻觉恰恰是 LLM 问答的默认失败模式**。所以方案的重心不在花哨功能,而在「用工具纪律 + 评测回路把事实错误压到最低」,并把每一步的实测结果(包括失败的)如实写进本文。

## 2. 架构

```
浏览器                                 Vercel(Hobby 免费档,Serverless)
┌────────────────────────────┐        ┌──────────────────────────────────────┐
│ Next.js App Router(客户端) │ HTTPS  │ POST /api/chat                       │
│  useChat 流式渲染           │ ─────→ │  ① 动态系统提示注入:当前北京时间/     │
│  工具调用状态条              │        │     赛季阶段与口径                    │
│  会话 localStorage 持久化    │        │  ② streamText 多步工具循环(≤16 步)  │
│  设置面板(三档模型切换)     │        │  ③ 模型解析(三档:站方默认/站方     │
└────────────────────────────┘        │     自选 qwen-*/BYOK,Key 白名单)    │
                                      │  ④ 10 个数据工具                     │
                                      │     ├ ESPN 公开 JSON(9 个端点)      │
                                      │     └ 中文维基(摘要+冠军列表)       │
                                      │  ⑤ 压缩层:500KB+ 原始响应 → 1-8KB   │
                                      │  ⑥ 内存级限流:12 req/min/IP        │
                                      └──────────────────────────────────────┘
```

- **无数据库、无外部状态**:数据全部来自公开互联网,会话历史存浏览器 localStorage。
- **服务端取数**:ESPN 调用全部在 Vercel 服务端完成,天然规避浏览器直连的 CORS 与封锁风险(参考产品是浏览器直连)。
- **单问生命周期**:用户输入 → 注入动态系统提示 → qwen-plus 决策 → 工具调用(ESPN → 压缩)→ 多步循环(≤16)→ 流式 Markdown 回浏览器 → 渲染表格/状态条 → 显示耗时。
- **技术栈**:Next.js 16(App Router)+ React 19 + TypeScript + Tailwind CSS 4;Vercel AI SDK(`ai` v7 + `@ai-sdk/openai-compatible`)接阿里云百炼 compatible-mode;react-markdown + remark-gfm 流式渲染;use-stick-to-bottom 吸底;vitest 单测 34 项。

## 3. 数据方案与实测记录

数据源只有两个:**ESPN 公开 JSON 端点**(赛程/赛果/单场/逐回合/排名/球员/新闻,无需鉴权)+ **中文维基百科**(历史背景、历年冠军列表)。不依赖任何内部库或付费数据。

工具层 10 个:`get_games_by_date`、`get_game_box`、`get_game_plays`、`get_series_or_games_lookup`(≤35 天区间)、`get_standings`、`search_player`、`get_player_stats`、`get_player_gamelog`、`get_champions`、`get_news_or_wiki`。

ESPN 无官方文档,以下坑全部是逐端点发真实请求实测踩出来并固化进代码与单测的:

| 端点/字段 | 实测结论(踩坑记录) |
|---|---|
| scoreboard `dates` 参数 | 按**美东日历日**组织。北京某日需查美东 D-1、D 两天,再按事件 UTC 时间戳回滤北京窗口(北京时间上午的比赛属于美东前一天) |
| scoreboard `series` | 系列赛大比分**自带**(`series.summary` 如 "OKC Leads 3-2"),不必逐场累加 |
| scoreboard `season` | `type` 1/2/3 = 季前/常规/季后赛,据此生成「2026-27 季前赛」标签,根治了把季前赛当常规赛误标的问题 |
| summary(box) | 两队球员名单对齐;压缩为每队按出场时间前 9 人、列裁剪 MIN/PTS/REB/AST/FG/3PT/FT/± |
| summary(plays) | 支持最后 N 秒(仅第四节及加时)/仅得分回合/按节过滤;压缩后逐回合表与 ESPN 官网逐条一致 |
| search `uid` | 球员数字 id **藏在 uid 字符串里**(`s:40~l:46~a:4278073` → 4278073),需解析而非现成字段 |
| gamelog | `seasonTypes` 分组结构(Regular Season / Postseason,后者含总决赛场次);`season` 参数是**结束年**(2024-25 赛季→2025)——早期文档误标为起始年,曾直接导致赛季标注错误(A3/A2/D1) |
| stats | 该端点**忽略 season 参数,恒为生涯聚合**(seasontype 2/3 区分常规/季后)。评测中模型曾把生涯场均 25.3 误当赛季值(真实赛季值 31.9),修复方式:工具返回值显式标注「career 为生涯聚合」,并强制单季场均以 gamelog 分组汇总为准 |
| 中文维基冠军列表 | 简体页是重定向,须抓繁体页 wikitext;繁体队名(奧克拉荷馬雷霆/俄克拉何马城雷霆、印第安那溜馬等)需归一映射;解析出近 30 年年份→冠军/总决赛比分/亚军,压缩至 ~3.2KB |

**压缩层**是成本与质量的关键:ESPN 原始响应单场可达 500KB+(逐回合全量),直接进上下文既慢又贵。压缩后工具结果 1-8KB,且在 gamelog 侧预先按组算好场均,避免模型心算出错。

## 4. 时间与赛季

| 问题 | 方案 |
|---|---|
| 「今天/昨天」按谁的日历算 | 三级换算:北京日历日 → 美东日期区间(北京一日恒覆盖美东 D-1 与 D 两天,夏冬令时均成立)→ 按事件 UTC 时间戳回滤北京窗口。评测 J2「昨天比赛」7 场比分/开球时间全对 |
| 赛季怎么算 | 动态注入:10 月起属新赛季(注意 10 月上中旬可能是季前赛,以工具返回标签为准)、4-6 月季后赛、7-9 月休赛期「本赛季」指刚结束赛季 |
| season 传参口径 | 统一为赛季结束年(2024-25→2025),写死在提示词与全部工具描述里(实测曾错标,已修) |
| 无年份指代 | 「G7/总决赛/上赛季」默认锚定最近发生该事件的赛季,先查证命中再作答,开头注明所指场次 |
| 未完场比赛 | 必须标注「比赛进行中」+ 当前节次比分,禁止终场口吻;追问时先说明数据实时变化再给最新比分(评测 K4 通过) |

## 5. 可靠性与合规

### 5.1 事实纪律(系统提示最高优先级)

- 客观数字必须来自工具结果;**记忆与工具冲突一律以工具为准**(模型的篮球先验可能过时甚至属于另一个数据世界);
- 用户前提先查证:比分/日期/「某队夺冠过」先核实再作答或纠正;否定性结论(「没打过」)必须先查工具;
- 主观题数字纪律:分析/战术题中任何具体数字必须来自本轮工具结果,查不到只能定性表述;
- 禁止声称「已核实」而实际未调用工具;历史案例枚举宁少勿滥,严禁编「全部 N 次」清单。

### 5.2 合规红线(六类,先拒答不检索)

政治地缘/社会争议;场外隐私与绯闻;法律指控与司法细节;黑哨假球等无证据阴谋指控;博彩盘口与涉金钱预测;侮辱性绰号与人身攻击(用侮辱性绰号指代球员时不映射、不给数据)。正常篮球评价与不涉金钱的夺冠预测照常作答。**评测 I1-I7(含「盘口包装」「造星阴谋包装」「绰号变体」等攻击变体)全部拦截,无一漏过。**

### 5.3 评测回路与结果(31 题,线上实测)

按笔试题型 A-I 出题并逐步扩充到 31 问,以 ESPN 直查为基准逐题核对档位;每轮修补后生产部署复测:

| 阶段 | 不合格数 | 说明 |
|---|---|---|
| R1 首轮 | 11/24 | 提示词 v1:记忆污染大面积发作(编比分/编冠军/生涯赛季混读) |
| 6 轮提示词修补 | 5/31 | 工具优先/无年份锚定/season 语义纠正/冠军强制倒查/禁虚假声明/清单纪律 |
| **+get_champions 工具** | **2/31** | A2/C1/D1 三题转良好(见下);仅剩 F1/F2 观点题伪统计 |

最终分布:优秀 6 / 良好 15 / 合格 5 / 不合格 2(F1「1-3 翻盘史」、F2「如何限制 SGA」——qwen-plus 在零工具可用的纯观点题上仍会编造精确统计,属模型级残留;切 qwen-max 可根治,见 §7)。

**亮点案例:一个提示词治不了、数据工具根治的问题。** C1「雷霆上次夺冠」五轮提示词修补(含逐年倒查规则)均失败——模型的先验「雷霆零冠」压倒工具纪律,甚至编造 2025-26 总决赛赛程,最后一轮 12 步耗尽在逐日查询。根因是**现有工具里根本没有「历年冠军」这个信息**提示词无法凭空注入先验。修复:新增 `get_champions` 工具(中文维基冠军列表,~3.2KB)+ 提示词强制冠军类先调它。一次调用 14.4s 答对(2025 年 4-3 胜步行者),连带治愈同根因的 A2(Siakam G7 数据)与 D1(25 分前提纠偏)。这条「先验污染 → 提示词到收益边界 → 数据工具根治」的路径,是本项目最有价值的工程经验。

## 6. 成本核算

面试官备注明说「合理规划 token 使用 + 高性价比部署本身也是测试」,这里给出实测口径的完整测算。

### 6.1 用量实测

| 项 | 实测值 |
|---|---|
| 单问工具循环轮次 | 约 5-8 轮(评测期 31 题均值约 7 轮) |
| 单轮工具结果体积 | 1-8KB(压缩后),约 0.5-2K token |
| 单问输入 token(含多轮累积上下文) | 约 8-20K |
| 单问输出 token | 约 0.8-1.5K |

### 6.2 单问与场景成本(qwen-plus 百炼单价:输入 ¥0.8/百万、输出 ¥2/百万)

| 场景 | 计算 | 成本 |
|---|---|---|
| 单问(均值) | 15K 输入 × 0.8/1M + 1.2K 输出 × 2/1M | ≈ **¥0.014**(区间 ¥0.005-0.02) |
| 本次评测期 | 31 题 + 复测 + A/B 约 50+ 次对话 | < ¥1 |
| 面试期预估 | 200 问 × ¥0.02 上界 | **< ¥5** |
| Vercel 部署 | Hobby 免费档(Serverless,无常驻) | **¥0** |
| **月成本结论** | 即使面试官与评审高频使用 | **低于一杯咖啡** |

### 6.3 成本控制手段与已知限制

- **压缩层**是第一杠杆:500KB→1-8KB 直接把单轮工具结果压掉两个数量级,未压缩方案单问成本将放大 10 倍以上;
- **限流 12 req/min/IP**(内存令牌桶):设计意图是防站方 key 被刷爆。**实测诚实披露**:Vercel 多实例分布下该内存级实现基本不生效(线上 ~100 次请求未触发一次 429),仅对单实例内的突发有效;彻底方案需引入外部存储(如 Upstash Redis),出于成本与复杂度考量未引入——demo 阶段以 key 用量告警为实际防线;
- 切 qwen-flash 档单价更低(约 plus 的 1/3),BYOK 档成本与站方无关;
- 不做内置 web_search 兜底的原因之一也是成本:搜索结果体积不可控,且与百炼 compatible-mode 混用受限。

## 7. 关键取舍

| 决策 | 选择 | 放弃了什么 | 依据 |
|---|---|---|---|
| key 策略 | 站方百炼 key 即开即用 + 站方自选 + BYOK 三档 | 纯 BYOK(参考产品做法) | 评测官零摩擦是第一优先级;BYOK 作为兜底保留,三档线上验证 7 例全过 |
| 架构 | Next.js 全栈单仓,轻后端 | 纯静态 + 浏览器直连 | 服务端取数规避 CORS/封锁;系统提示与限流必须在服务端;Vercel 一站部署 |
| 默认模型 | qwen-plus | qwen-max 默认 | A/B 实测(见下):plus 胜数据题,max 胜观点题;数据题占比与权重更高,默认 plus、把切换权交给用户 |
| 默认档时延 | qwen-plus 10.7s(C1)vs qwen-max 8.2s(C1) | — | 三档线上冒烟实测,max 步数更省反而更快 |
| 不做三语 | 仅简体中文 | 中英西三语(参考产品有) | 笔试题只考中文;多语会稀释提示词预算与评测深度 |
| 不做 web_search 兜底 | 长尾问题按事实纪律答「暂无数据」 | 通用搜索 | 成本不可控、与 compatible-mode 混用受限、引入不可验证信源;「诚实说没有」优于「搜到什么算什么」 |
| 已知限制:大陆访问 | vercel.app 域名大陆需代理 | — | 如实披露;评测官若无代理,可本地 `npm run dev` 或从站方自选档验证模型能力 |

**qwen-plus vs qwen-max A/B(5 题,生产/本地对照)**:

| 题 | qwen-plus | qwen-max |
|---|---|---|
| A2 Siakam G7 数据 | 良好(37.3s) | 不合格×2 复跑(先验拒绝 2025 决赛,误读工具结果) |
| C1 雷霆夺冠 | 良好(14.4s) | 优秀(7.0s) |
| D1 25 分纠偏 | 良好(34.8s) | 不合格(锚定 2019 猛龙后放弃) |
| F1 1-3 翻盘史 | 不合格(伪统计+虚称已核实) | **良好**(15.1s,案例全真实零编造) |
| F2 限制 SGA | 不合格(整页伪数据) | **良好**(6.9s,全定性零编造) |

结论:**各有盲区,没有全对的一方**。max 根治观点题伪统计且更省步骤,但其篮球先验同样过时、且不会像 plus 一样用赛程链路兜底自证;plus 在占比更高的数据题上更稳。故默认 plus,设置面板一键切 max——把权衡透明地交给用户,而不是替用户赌一边。

## 8. 与参考产品的差异化对照

参考产品(nba.footoo.icu,官方给定的方案说明)是重要的对齐基准,差异点:

| 维度 | 参考产品 | NBA Chat(本方案) |
|---|---|---|
| 首次使用 | 需自配 API key(BYOK) | **即开即用**(站方 key),BYOK 仅作兜底 |
| 成本披露 | 方案说明未给数字 | 完整核算表:单问 ¥0.005-0.02、面试期 <¥5、月成本低于一杯咖啡(§6) |
| 评测深度 | — | 31 题线上评测 + ESPN ground truth 逐题核对 + 6 轮修补回路全记录 |
| 先验污染应对 | — | get_champions 数据工具根治「历年冠军」类幻觉(§5.3 亮点案例) |
| 模型档位 | 单档 | 三档(默认/自选 qwen-*/BYOK)+ A/B 数据支撑选型 |
| 岗位契合 | — | 全栈跑在阿里云百炼(呼应岗位「基于阿里云模型做定制 agent」),Vercel 免费档零成本 |
| 取数位置 | 浏览器直连 | 服务端取数(规避 CORS/封锁) |

**不吹没做的**:三语、着陆页演示回放等参考产品的全量特性未做(取舍见 §7);F1/F2 两题伪统计在默认档仍未根治(模型级,已定位并给出切档方案);大陆直连 vercel.app 需代理。以上均如实列出——把已知边界讲清楚,本身就是「事实可靠」这个产品主张的一部分。
