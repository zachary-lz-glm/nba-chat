## 1. 背景与目标

NBA 招聘笔试题:从零独立复刻一个 NBA 官方风格的中文智能问答产品(NBA Chat),交付**可在线访问的部署链接 + 简要方案说明 PDF**。

面试官从两个维度打分:

| 维度 | 构成 |
|---|---|
| 可用性(回答质量) | 题意理解 20% · 事实准确性 20% · 完整性 15% · 性能/时延 15% · 多轮一致性 10% · 表达规范 10% · 结构可读性 10% · **安全合规一票否决** |
| 产品交互/UI 视觉 | 美观度、流式输出、加载/错误反馈、结构化排版、多轮体验 |

硬性要求(题目 4.1):联网取数(公开互联网,无内部库)、聊天式 Web 界面多轮对话、合规兜底(2.4 六类红线)。

### 隐藏考点(面试官备注原文归纳)

1. token 成本规划 + 高性价比部署本身是考察项(「合理规划 token 使用+找一个简单性价比高的部署方式,本身也是一种测试」)
2. 面试官点名 Vercel 免费额度、大模型试用 API、前后端一站部署连 GitHub
3. 岗位背景:阿里云提供底层算力与技术支持,NBA 做定制化开发

## 2. 已确认的关键决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 推理付费/部署 | **站方 key 即开即用 + BYOK 兜底**,部署 Vercel 免费档 | 面试官打开链接即用、零摩擦;正中面试官提示;参考产品是 BYOK 反而有评测摩擦,形成差异化 |
| 默认模型 | **阿里云百炼 Qwen,默认档 qwen-plus**(OpenAI compatible-mode;BYOK 面板可选 qwen-flash 等更快/更省档) | 呼应岗位(阿里云算力);面试问题 1「基于阿里云模型做定制 agent」直接拿本 demo 当案例;百炼有免费额度、后续单价低;选 plus 而非 flash 是因为事实准确性 20% 权重押在多步工具循环质量上 |
| 时间预算 | **一周打磨版** | 核心范围 + 体验打磨 + 1-2 个差异化亮点;三语、着陆页演示回放等参考产品的全量细节不做 |
| 架构 | **方案 A:Next.js 全栈单仓** | 即开即用→需要轻后端→Next.js API Route + AI SDK 最顺;Vercel 一站部署 |

### 差异化亮点(押注)

1. **即开即用 vs 参考产品 BYOK 摩擦** —— 评测体验直接胜出,方案说明中正面对比
2. **成本核算表** —— 面试官备注明说成本意识是考点,但参考方案说明未给数字;我们在 PDF 给出 token 用量 × 单价 × 预估面试流量 → 成本测算与限流策略
3. **UI 打磨(用户明确要求)** —— 用已安装的 UI skill 在实现阶段系统性打磨(见 §9)

## 3. 架构

```
浏览器                              Vercel(免费 Hobby 档)
┌──────────────────────────┐       ┌────────────────────────────────┐
│ Next.js App Router (客户端)│ HTTPS │ /api/chat(Serverless Route)    │
│  useChat 流式渲染          │ ────→ │  动态系统提示(时间/赛季注入)     │
│  工具调用状态条             │       │  streamText 多步工具循环(≤12 步)│
│  会话 localStorage 持久化   │       │  ├ 默认:服务端预置百炼 Qwen key │
│  设置面板(BYOK 可覆盖)     │       │  └ BYOK:请求携带用户配置覆盖    │
└──────────────────────────┘       │ 9 个数据工具 → ESPN/Wikipedia   │
                                   │  压缩层:500KB+ → 1-8KB 摘要    │
                                   │  简单内存限流(防站方 key 被刷)   │
                                   └────────────────────────────────┘
```

无数据库、无外部状态。数据全部来自公开互联网(ESPN 公开 JSON、Wikipedia REST)。

## 4. 技术栈

- Next.js 15(App Router)+ TypeScript + Tailwind CSS
- Vercel AI SDK:`ai` + `@ai-sdk/openai-compatible`(百炼 compatible-mode;BYOK 时直连用户指定的 OpenAI 兼容服务)
- Markdown 流式渲染(react-markdown + remark-gfm,或 streamdown,实现时按质量择优)
- use-stick-to-bottom 自动吸底
- vitest 单测;ESPN 端点实测用 Node 脚本

## 5. 组件设计

### 5.1 服务端

| 模块 | 职责 |
|---|---|
| `app/api/chat/route.ts` | POST 入口:组装系统提示、读取 BYOK 覆盖配置、streamText 工具循环(maxSteps=12)、限流 |
| `lib/espn/` | ESPN 客户端:按日赛程/赛果(scoreboard)、单场 summary(box+逐回合)、排名/数据榜、球员搜索/档案/逐场、新闻。全部带类型、超时与结构化错误 |
| `lib/compress/` | 压缩层:逐回合按「最后 N 分钟/得分回合/单节」过滤;box score 裁剪为关键列;排名裁剪;目标 1-8KB |
| `lib/time.ts` | 北京↔美东↔UTC 换算;「北京日期→美东日期区间查询→按 UTC 时间戳回滤」;当前赛季计算(10 月开赛跨年,格式 2025-26;7-9 月休赛期「本赛季」指刚结束赛季) |
| `lib/prompt.ts` | 系统提示构建,内容见 §7 |
| `lib/rl.ts` | 每 IP 简单令牌桶,默认 12 请求/分钟(Serverless 实例内存级,仅尽最大努力;方案说明如实说明局限) |

### 5.2 客户端

- 聊天主界面:流式逐字渲染、转播风 Markdown 表格(红表头线/斑马行/等宽数字)、工具调用状态条(「正在查证 6月14日 赛程…」)、响应耗时显示
- 会话抽屉:自动命名、切换/删除/新建,localStorage 持久化,上下文按会话隔离
- 设置面板:服务商预设/接口地址/模型/Key/测试连接;不配置则走站方 Qwen;Key 仅存 localStorage
- 交互细节:停止生成、重新生成、一键复制、中文输入法回车保护(IME composition 期间不发送)、错误气泡+重试、移动端适配、键盘可达性

### 5.3 数据工具层(9 个)

| 工具 | 支撑题型 |
|---|---|
| `get_games_by_date`(含系列赛大比分推导) | B 赛程/赛果 |
| `get_box_score` | A 单场球员数据 |
| `get_plays`(最后 N 秒/得分回合/单节过滤) | E 逐回合/关键球 |
| `get_standings` | 排名/数据榜 |
| `search_player` / `get_player_stats` | A/C 球员档案、本季/季后赛/生涯 |
| `get_player_gamelog` | 连胜连败等累计推导 |
| `get_news` | 新闻/长尾 |
| `get_wiki_summary` | C 历史背景 |

**显式取舍**:不做内置 web_search 兜底(百炼 compatible-mode 与内置搜索混用受限、成本不可控);长尾问题按事实纪律答「暂无数据」。理由写入方案说明。

## 6. 数据流(单问生命周期)

用户输入 → `POST /api/chat`(注入动态系统提示 + 会话历史)→ Qwen 决策 → 工具调用(ESPN → 压缩)→ 多步循环(≤12)→ 流式 Markdown 回浏览器 → useChat 渲染 + 工具状态条 → 完成后显示耗时。

时区处理链:北京日历日 → 美东日期区间查询 → 按事件 UTC 时间戳换算回北京日期精确过滤(规避「北京时间早上的比赛属于美东前一天」错位)。

## 7. 系统提示词设计(对应笔试 2.1–2.4)

1. **身份**:NBA 官方风格问答助手,客观/专业/数据驱动/中立;简体中文,专有名词可保留英文;称呼「您」;不暴露数据来源/接口/字段等内部细节
2. **事实纪律(最高优先级)**:客观数字必须来自工具结果、严禁凭记忆作答、查不到如实说「暂无数据」;系列赛比分/连胜连败/关键球必须逐场逐回合核对;用户叙述的比分日期先查证,有误礼貌纠正,「没查到」≠「用户说错」;主观比较题只分维度罗列客观维度
3. **时效注入**:每轮动态注入当前北京时间/美东时间;赛季规则(10 月开赛、次年 6 月收官、休赛期口径);「现任总冠军/最近夺冠」结合当前赛季进程
4. **合规红线**:六类话题(政治地缘/隐私八卦/司法/黑哨阴谋/博彩/侮辱性绰号与人身攻击)一律**先拒答、不检索**,1-2 句礼貌说明并引导回赛场;正常篮球评价与非金钱预测照常作答
5. **表达规范**:先结论后展开;标题/列表/表格;关键数字加粗;避免冗长

## 8. 错误处理与测试

**错误处理**:ESPN 超时/5xx → 工具返回结构化错误 → 模型转译「暂无数据/稍后再试」;LLM 上游错误 → 前端错误气泡 + 重试;限流 → 429 友好提示;BYOK 配错 → 「测试连接」即时反馈。

**测试策略**:
- 端点实测脚本:对 ESPN 每个端点跑真实请求,固化字段语义/覆盖深度/时区行为结论(自己重新验证,不轻信参考文档)
- vitest:时间换算、赛季计算、压缩函数
- 评测清单:按笔试题型 A–I 各出 3–5 题人工跑分(对齐评分维度);合规红线题逐条验证拦截

## 9. UI 质量计划(用户明确要求,占评分一半)

实现阶段按序调用已安装的 UI skill,不裸写 UI:

1. **design-taste-frontend** —— 立审美方向(反模板味):深夜球馆底色 + NBA 官方红蓝 + 硬木地板点缀的转播图文风(方向可调,避免与参考产品视觉雷同)
2. **high-end-visual-design** —— 字体/间距/阴影/卡片质感,让界面「贵」
3. **frontend-ui-engineering** —— 工程质量:可达性、响应式、状态管理、生产级组件
4. **impeccable** —— 上线前批判性审查:层级/留白/动效/微交互/空态/错误态逐项过
